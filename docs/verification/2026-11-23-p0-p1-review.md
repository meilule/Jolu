## 2. 后端代码复查

### 2.1 建议优先处理

#### C-1 网关请求路径用阻塞锁等数据库

位置：

- `gateway/wire.rs:391` `record_route` 写流水：由原来的 `try_lock` 改成了 `lock()` 一直等。
- `gateway/route_log.rs:173` `CancelWatch::new` 的取消回调：在 `Drop` 里 `lock()`。注释写「拿不到锁就跳过」，与代码不符。
- `gateway/activity.rs:41` `allocate_request_uid`：在 `wire.rs:485` 和 `adapter/gemini.rs:46` 被调用，每个请求选路之前都要先拿一次锁。

影响：`ProxyDeps.db` 是 `Arc<Mutex<rusqlite::Connection>>`，采集器扫描期间一直持有它（C-3 会让持锁更久）。这段时间里，转发中的请求会阻塞 tokio 工作线程，流式请求的首字也会被推迟。工作线程全被占住时，其他请求同样受影响。

建议：

1. 流水写入和取消改判改走 `tokio::task::spawn_blocking`，或者交给一个专门写库的通道（mpsc + 单写线程），请求路径不再等锁。
2. `request_uid` 改为启动时一次向数据库预留一段号码（例如 1,000 个），之后在内存里原子递增，用完再预留下一段。空号没有影响，请求路径不碰锁，跨进程唯一性由数据库的预留保证。
3. 测试 `route_record_waits_for_busy_database` 现在锁定的是「阻塞等待」，改了以后要换成「库忙时异步写入，最终不丢」。

#### C-2 上游中途报错会被记成「已取消」（推断）

位置：`gateway/route_log.rs` 的 `CancelWatch`（文档表在第 116 行起）。

问题：文档表说上游中途报错（`Ready(Some(Err))`）「由 `record_route` 已有的失败分支处理」，但那时这一行早已写成 `ok`。`poll_next` 收到 `Err` 时没有清掉 `on_cancel`，hyper 随后丢弃 body，`Drop` 触发回调，这一行就被改成 `cancelled`。上游错误被说成了客户端断开。

建议：

- `poll_next` 收到 `Ready(Some(Err(_)))` 时，把这一行改判为 `failed`（同样只改 `ok` 行），并清掉取消回调。
- 补测试：上游流吐出一个 `Err` 后结束，断言结果是 `failed` 而不是 `cancelled`。

另一个风险需要真机核实：有的客户端收到流里的结束事件（Anthropic `message_stop`、OpenAI `data: [DONE]`）后，不等流读到 `None` 就关闭连接，这会被误报为取消。需要用真实的 Claude Code 和 Codex 各抓一次。如果确实会误报，就把「已转发结束事件」也算作读完。

#### C-3 Qoder 账本每轮整份重读重写

位置：`native_sources.rs:1210` 的 Qoder 分支。

问题：每次扫描都把 `chat_message` 全部读出、逐行解析 JSON、再整批交给 `source_store::write`。现在约 1,000 行，之后还会增长，每轮都会延长 C-1 里的持锁时间。

建议：照搬 ZCode 已有的 `db_stamps` / `db_unchanged` / `save_db_stamps`（`native_sources.rs:341` 起），主库或 WAL 有变化才重读。整份重建的语义（应对客户端改写或清理）可以保留，只是变成「有变化才做」。

### 2.2 数据正确性

#### C-4 Qoder `total_tokens` 会把半个数当成完整总数

位置：`qoder_usage.rs:105-109`。

```rust
let total = prompt.zip(completion).map(|(p, c)| p + c).or(completion).or(prompt);
```

只有 completion 或只有 prompt 时，用这一项充当 total，入库后会被当成已知总量。按「未知不是零」的规则，两项缺一项时 total 应为 `None`。建议去掉两个 `.or(...)`，并补一条测试。

#### C-5 Qoder 坏行：一类被静默跳过，另一类拖垮整个来源

位置：`qoder_usage.rs:69-86`。

- `token_info` 不是合法 JSON 时直接 `continue`，没有计数，也不报错。
- `session_id`、`id` 只要有一行是 NULL，`r.get::<_, String>` 就会让整个 `read_usage` 返回错误，这一轮 Qoder 一条都采不到。

建议：两种情况都跳过这一行并计数，计数放进扫描结果的 `errors`（与 `scan_files` 的做法一致），各补一条测试。

#### C-6 `Coverage` 的约束谁都能破坏

位置：`data_contract.rs`；`db.rs` 的 `today_token_coverage`（约第 1380 行）。

问题：注释要求 `known == 0` 时 `total` 必须为 `None`，但字段是公开的，`with_total` 可以塞任意值。`today_token_coverage` 也是先构造出 `total: None, known > 0` 这种违反约束的中间状态，再在 `live_usage` 里补总量。

建议：

- 字段改为私有，只留两个构造入口：`of()`，以及一个会校验的 `from_counts(known, unknown, total)`（违反约束时把 total 置 `None`）。
- 顺手可以收拾：`state()` 和 `complete()` 判断逻辑重复，`complete()` 可以直接等于 `state() == "known"`；`today_token_coverage` 为参数个数不同写了两个分支，可以改用 `params_from_iter`；`period_range` 在 `live_usage` 里被调了两次。

#### C-7 Qoder 新旧去重键的注释与事实不符

位置：`qoder_usage.rs:46-47` 的注释说 `{session_id}:{message_id}` 与 `native_parse::qoder` 的 `{session}:{id}`「一致，便于共存」。旧解析器实际优先用 `request_id`（`native_parse.rs:107`），两者并不一致。

建议：先改注释，避免误导；统一去重键和旧记录迁移按 P-9 处理。

### 2.3 低优先级（可以不动）

- `day_overview` 和 `counts_since` 现在全表扫描，也不按时间过滤。流水最多 1,000 行（`KEEP_ROWS`），开销可以忽略；如果以后调大上限，再加时间条件。
- 迁移里的 `let _ = conn.execute("ALTER TABLE ... ADD COLUMN ...")` 会吞掉所有错误，不只是「列已存在」。这是沿用的旧写法，要改就统一改成先查 `pragma_table_info`。
- 几条新测试（`a_delayed_scan_picks_up_new_rows_without_duplicating`、`qoder_source_is_available_from_the_ledger_alone` 等）在结尾才清理临时目录，测试失败时会留下残留文件。可以改用 drop guard 自动清理。

# Jolu 产品定位与功能边界

日期：2026-11-23

状态：产品定位基线；功能实施状态以代码和最新验收记录为准

配套执行计划：[产品对齐执行计划](../plans/2026-11-23-product-alignment-execution-plan.md)

## 1. 一句话定位

Jolu 是一个 Windows 桌面 AI 工具管理器。它帮助用户连接和管理多个 AI 账号，看清额度、用量与会话，并把账号池中可用的模型接入其他 Agent。灵动岛是用户随时观察和操作这些信息的特色入口。

本文锁定的是产品目标和功能范围，不能把目标直接当作所有平台均已实现。具体平台的支持情况必须依据能力矩阵与验收结果展示。

## 2. 目标用户与核心价值

- 同时使用多个 AI 账号、订阅或 API 来源的个人用户。
- 在多个 Agent 之间切换，希望集中使用模型额度与管理工具的用户。
- 希望知道额度消耗、当前会话和请求去向的用户。

用户的主要路径是：连接账号 → 确认可用额度和模型 → 将模型接入 Agent → 使用 Agent → 在灵动岛、用量和会话页面了解发生了什么 → 在需要时签到、继续会话或调整路由。

## 3. 已确认的产品功能

| 功能 | 用户希望完成的事 | 产品要求 |
| --- | --- | --- |
| 账号与额度 | 在一处连接、保存多个账号并查看额度 | 每个连接独立识别，标明平台、账号、授权状态、额度来源和更新时间。能力随平台而异 |
| 灵动岛 | 随时看到额度、Token 消耗及交互状态 | 与账号、路由、会话联动，展示可确认的信息及其状态。经典和胶囊样式遵循现有设计约束 |
| 签到 | 为已连接且支持官方活动的账号签到 | 展示是否支持、签到结果及来源。自动签到是否扩展不由本文决定 |
| 用量统计 | 看懂不同工具和账号的使用情况 | 明确数据来自原生记录、Jolu 路由还是官方接口，保留时间范围、单位、覆盖范围及未知状态 |
| 会话线程 | 找到会话并在可支持的工具中延续 | 区分查看、在原工具继续和跨工具交接，各项能力按工具实际支持情况展示 |
| Skills 管理 | 集中查看和管理各工具的 Skills | 展示作用范围、目标工具与可写能力，保留用户已有文件和配置 |
| Agent 与模型路由 | 将账号池中的模型提供给其他 Agent | 管理模型来源、接入、选路及运行状态，说明请求实际走向，支持能力按来源和 Agent 分别验证 |

账号池是可以参与模型调用的账号和来源集合。Agent 是使用模型的工具。连接账号、查看额度与将其作为路由来源是相关但各自需要验证的能力，不能因其中一项可用就推定其他项也可用。

## 4. 工具调用和 MCP

用户希望通过 Jolu 接入模型后，Agent 的联网等工具能力仍能工作。这里涉及 Agent 发起工具调用、模型返回工具请求、工具实际执行、结果回传和后续回答，整条链路都需验证。

当前代码已有搜索 / 抓取 MCP、部分服务端联网工具代执行以及 Claude 订阅工具桥，覆盖范围不同。应先以真实链路和协议矩阵确认可用范围，再决定通用 MCP 管理及路由器的产品形态。MCP 管理、按 Agent 分发与按需发现是参考方向，具体功能、界面和资源 / 提示词支持范围待产品设计确认。

## 5. 数据可信度原则

1. 每项数据保留来源、采集时间和覆盖范围。平台官方额度、Agent 本地记录和经过 Jolu 路由的记录分别描述各自看到的情况。
2. 已知零、未知、估算、过期、采集失败和不支持应能区分。未知账号归属保持未知，不能根据相近时间或模型名当作确定归属。
3. 跨组件共享同一套语义与身份映射，让用量、会话、路由和灵动岛读到可解释的数据。具体存储和同步方式由执行阶段根据现有架构决定。
4. 一次用户请求可能有多个路由尝试。同一条记录被重复扫描或被多个来源观察到时，需要依据可证明的身份去重，同时保留必要的尝试信息。
5. 展示的数据范围必须与采集范围相符。历史被源端清理、采集延迟、上游未返回用量或本地权限不足时，应能解释缺口。

## 6. 当前能力基线与待核实事项

截至本文日期，代码和现有记录显示 Jolu 已具备多账号连接、路由来源、路由分组、重试和会话亲和等基础；用量和会话已有原生来源采集；MCP 和工具桥已有部分实现。不同平台的完整程度与验证强度不同。

- 2026-11-22 的 ZCode 只读对账中，源库 17,127 条请求均可按 ID 在 Jolu 找到，共有记录的开始时间和终态差异为零。Jolu 另外保留了源端已清理的历史。这个结果限定于当次数据与所核对字段，详见 [用量准确性计划第 11 节](../plans/2026-11-21-usage-data-accuracy-plan.md)。
- 活跃会话观察的既有计划已记录阶段性实施，后续工作应先对照最新记录与代码。见 [活跃会话观察计划](../plans/2026-11-21-active-session-observation-plan.md)。
- Qoder、Trae 等部分订阅转发仍需真实账号验收。功能存在、合成测试通过、真实账号通过属于不同状态。见 [未验证集成清单](../todo/2026-10-22-unverified-integrations.md)。
- 路由分组的额度节奏策略目前需要进一步评估额度值、更新时间及单位。网关流水保留范围和重试记录也需要与统计口径核对。

## 7. 产品取舍与优先级

建议先让现有功能的数据可信、路由可解释、工具链可验证，再扩展通用 MCP 管理和跨 Agent 交接。具体顺序、依赖和验收见执行计划。

Jolu 面向桌面个人使用场景。支付、商业售卖和服务器运营能力不属于本次已确认目标。支持某个功能不意味着需要在所有 Agent 上提供完全相同的技术实现，应公平展示每家的真实能力和限制。

## 8. 安全、设计和待决事项

- 账号凭据和客户端密钥按现有安全机制管理，不写入日志、截图或验收样本。涉及授权、服务条款和计费的实际行为以各平台当前规则及用户授权为准。
- 主窗口设计以 `docs/ui/Jolu.pen` 为唯一依据，只能通过 Pencil MCP 读取。画板缺少的界面或状态标记「待确认」，未经用户明确要求不修改设计稿。
- 待确认的产品决策包括通用 MCP 管理的界面和支持范围、跨 Agent 交接的体验、账号池自动切换的默认策略，以及不同来源数据如何在界面上呈现。执行前先复用已有设计与行为，涉及新界面按设计规范处理。
